## 一、背景与目标

预算规则页已完成三 Tab 重构（当前版本 / 历史版本 / 适用经济事项），其中 Tab3 已把「规则卡 ↔ 经济事项」映射落库（`rule_item_event`）。

本次新增**第 4 个 Tab「创建明年新规则」**，把"编明年预算规则"从纯手工克隆升级为**政策驱动 + AI 抽取辅助生成**：

- 用户导入集体的新预算政策文件（PDF/Word/Excel/图片）
- 系统结合「最新的规则↔经济事项映射（Tab3 event-map）」+ 政策文件文本
- 调用抽取（本期为正则占位 `extractRuleProposals`，真 LLM 后续接入）生成建议变更清单
- 基于当前 active 版本克隆出**草案版本（draft）**，应用建议 → 用 Tab1 同款卡片预览
- 人核对 → 点「正式发布」才置为 active（守"提示非判定"铁律）

目标年度固定为**明年**（系统自动取当前年 +1 = 2027），无需手选。

## 三、页面结构（新增 Tab4）

入口：`#rules` 内第 4 个 Tab（权限 `requireRuleEditor` 写；登录可读预览）。Tab 导航顺序：当前版本 / 历史版本 / 适用经济事项 / **创建明年新规则**。

### Tab4 · 创建明年新规则
- **顶部说明条**：展示目标年度「2027 年度」，来源注明「基于当前生效版本 + 导入政策文件 + AI 抽取」。
- **区块 A · 导入政策文件**
  - 上传控件（支持多文件：PDF / Word / Excel / 图片扫描件）
  - 调 `POST /api/policy-upload` 解析为文本；展示提取文本（可手动编辑/补全）
  - 支持"粘贴文本"兜底（无文件时直接填文本框）
- **区块 B · AI 抽取结果（建议变更清单）**
  - 调 `POST /api/rule-versions/:id/extract`（传 policyText）→ 返回 proposals
  - 列表展示：`scopeKey（可匹配则显示，含现行 factor/logic） → 建议 factor / logic`（如 食堂 现行 0.97 → 建议 0.95「较现行下降 2%」）
  - 人可逐项微调 factor（守"AI 不直写库"，最终由人确认）
- **区块 C · 草案预览（复用 Tab1 卡片）**
  - 点「生成草案版本」→ 后端克隆 active 为 draft + 应用 proposals（baseline 项 factor/logic 更新，flow 项默认继承）→ 返回 draftId
  - 用 **Tab1 同款卡片**（`renderRuleCards`）渲染该 draft：上部基线因子卡（单选 + 解释区）+ 下部 flow 子区
  - 草案版本名：`2027 年度预算规则（政策 AI 生成）`；`source_type='ai_policy'`；`effective_date=2027-01-01`
  - event-map：默认**继承当前 active 版本的映射**（待定稿项④），Preview 区可展示"本版本适用事项"
- **操作**
  - 「生成草案版本」：建 draft（未发布）
  - 「正式发布」：调 `POST /api/rule-versions/:id/publish` → 原 active 转 archived，草案置 active；发布后 Tab4 提示"已发布为当前生效版本"，Tab1/Tab2 同步可见
  - 发布前「丢弃草案」：删除该 draft（复用 DELETE 守卫，draft 可删）

## 四、关键设计决策（枚举备选 + 推荐）

### 决策 D1 · 草案生成实现方式
- **方案 A（推荐·分步编排）**：复用现有端点，前端编排 `extract` → `POST /api/rule-versions`（clone active 得 draftId）→ `PUT /api/rule-versions/:id/items`（apply proposals）→ 预览。改动最小、复用度高、易回归测试。
- **方案 B（一步聚合）**：新增 `POST /api/rule-versions/ai-generate` 后端聚合 clone+apply。封装更干净，但新增端点、需单独测。
- **推荐 A**：符合"改动必有回归测试"与最小侵入；真 LLM 接入时仅替换 extract 内部，不动编排。

### 决策 D2 · 抽取结果如何映射到 scopeKey
- 正则 `extractRuleProposals` 当前只产 `{hint, pct, factor, logic}`，**无 scopeKey**。
- **增强**：内置 `hint → scopeKey` 词典（食堂→canteen、宿舍→dorm、办公→down5、餐饮→canteen、绿化→green、收入→revenue、据实→actual 等），匹配到则带 `scopeKey`；匹配不到则 `scopeKey:null`，前端提示"请人工指定适用规则卡"。
- 真 LLM 接入后由模型直接输出 scopeKey，词典作兜底护栏。

## 五、数据模型改动（仅新增，不改现有表）

1. **版本号跨年**：`nextVersionLabel(db)` 当前写死 `v2026.%`。改为 `nextVersionLabel(db, year)` 按目标年生成 `v{year}.0`（该年前缀已存在则递增）。generate 流程传 `year=明年`。
2. **（可选）审计表 `policy_document`**（待定稿项②）：
```sql
CREATE TABLE IF NOT EXISTS policy_document (
  id         INTEGER PRIMARY KEY AUTOINCREMENT,
  version_id INTEGER,            -- 关联生成的草案/版本（发布后回填）
  filename   TEXT,
  text       TEXT,               -- 解析后的政策文本（AI 抽取依据，可追溯）
  created_at TEXT DEFAULT (datetime('now','localtime'))
);
```
> 用于留存"AI 生成依据"，契合项目可审计要求；若不上该表，文本仅前端暂存、不落库。

## 六、API 改动

| 方法 | 路径 | 说明 | 权限 |
|---|---|---|---|
| POST | `/api/policy-upload` | multipart 上传政策文件 → 调 markitdown(+vision) 解析 → 返回 `{text}` | requireRuleEditor |
| POST | `/api/rule-versions/:id/extract` | **已有**，本期增强返回带 `scopeKey`（词典映射） | requireRuleEditor |
| POST | `/api/rule-versions` | **已有**（clone active→draft），generate 流程复用 | requireRuleEditor |
| PUT | `/api/rule-versions/:id/items` | **已有**，apply proposals 到 baseline 项 | requireRuleEditor |
| POST | `/api/rule-versions/:id/publish` | **已有**，人点发布置 active | requireRuleEditor |

> 仅需**新增** `POST /api/policy-upload` 一个端点；其余全部复用现有端点。

**文件解析实现（policy-upload）**：
- node 接收 multipart（新增轻量 multer 或原生解析）→ 存 `runtime/tmp/` → spawn python（default venv 已装 markitdown）`markitdown <file>` 取文本；图片类先经 vision/OCR 脚本转文本
- 返回纯文本；解析失败返回 4xx + 原因
- 不持久化文件本体（仅文本），符合"最小化"原则
