### 1.2 三个核心问题

1. **语义漂移**：`adminHead` 前后端描述不一致——前端按 V2「公司行政负责人（组织编制/解释差异/落实压降）」定义，后端却按「行政归口负责人（归口科目管理）」定义，二者是不同角色。

## 2. 目标角色模型（14 角色收敛）

### 2.1 标准角色（9 个 role code + 18 个实例参数）

| # | code | 名称 | 层级 | scope | 实例参数 | 核心职责（V2 §2.1） |
|---|---|---|---|---|---|---|
| 1 | `ceo` | 集团 CEO/管理层 | 集团层 | group | — | 看全局报表 → 触发压降目标 → 重大争议最终决策/批准 → 看风险与决算 |
| 2 | `cooLead` | 集团总经办负责人 | 集团层 | group | — | 接收法人预算组织审核 → 牵头协商闭环 → 推动压降分解 → 统一收口管理口径 |
| 3 | `cooAnalyst` | 集团总经办预算管理员 | 集团层 | group | — | 汇总各法人数据 → 维护主数据/规则引擎 → 执行导入核对 → 对标/碰撞支持 |
| 4 | `legalHead` | 法人公司负责人 | 法人层 | company | `scopeCompany` | 审核本公司预算 → 响应压降参与协商 → 重大调整审批 |
| 5 | `adminHead` | 公司行政负责人 | 法人层 | company | `scopeCompany` | 组织/推动部门编制 → 解释预算 vs 实际差异 → 落实压降 |
| 6 | `companyBudgeter` | 公司预算管理员 | 法人层 | company | `scopeCompany` | 下发模板 → 汇总校验 → 规则偏离校验 → 提交 → 维护执行导入 |
| 7 | `centerOwner` | 职能中心归口责任人 | 归口层 | center | `centerId`（11 中心） | 维护归口科目编制逻辑 → 跨公司查看归口科目 → 降本分解跟踪 → 双口径对账 → 归口 AI 风险 |
| 8 | `expense` | 基层费用责任岗 | 基层层 | self | `expenseType`（7 类） | 一次填报最细经济事项 → 月度分解 → 规则预填+偏离记录 → 双派生视角 → 解释差异 |
| 9 | `admin` | 系统管理员 | 平台层 | all | — | 账户/组织/角色管理 · 平台运维 |

> **计数口径**：V2 §2.1 的「14 角色」= 集团 3 + 法人 3 + 归口 1 类 + 基层 7 类。代码层面归口与基层是「1 类角色 × N 实例」（`centerOwner` × 11 中心、`expense` × 7 岗位），故 role code 为 9 个（含平台 admin），实例共 18 个。归口 11 中心完整清单客户未供数（V2 §8-15），暂用 `data.js` 已有 11 个占位样例，待供数替换。

## 3. 关键设计决策

### R1 · 冗余角色处理：删除 vs 保留兼容

| 方案 | 说明 | 优点 | 风险 | 结论 |
|---|---|---|---|---|
| A. 删除（收敛） | 5 个冗余 code 下线，职责映射到标准角色，seed 用户重映射 | 单一真源、消除漂移；权限闸门只维护一份 | 破坏性变更，需重映射 seed 用户 + 清理前端引用 | ★ 推荐 |
| B. 保留兼容 | 冗余 code 标记 deprecated，标准角色为主 | 改动小 | 长期双轨，漂移继续 | 不取 |

**推荐 A 理由**：demo 是内部验证前端，无需向后兼容；「完整重构」的拍板本意就是收敛，保留兼容与拍板方向冲突。

### R2 · 角色定义单一真源：后端 role 表 vs 前后端各一份

| 方案 | 说明 | 优点 | 风险 | 结论 |
|---|---|---|---|---|
| A. 后端 role 表为唯一真源 | 前端真实登录后从 `GET /api/auth/me` 拉 roles（含 views/scope）；`BM.ROLES` 仅作演示通道（未登录）静态回退 | 消除前后端漂移 | 演示通道需同步维护一份回退字典 | ★ 推荐 |
| B. 前后端各维护 | 现状 | — | 已证实漂移 | 不取 |

**推荐 A 理由**：本次漂移正是前后端两份字典失控所致；收敛为「后端唯一真源 + 前端演示回退」，回退字典由同一收敛脚本生成，避免再次漂移。

### R3 · 归口/基层实例化：参数化 vs 实例化 role code

| 方案 | 说明 | 优点 | 风险 | 结论 |
|---|---|---|---|---|
| A. 参数化（现状延续） | `centerOwner` + `centerId`、`expense` + `expenseType`，1 类角色 × N 实例 | code 精简、权限矩阵单一 | 实例参数需纳入权限判断上下文 | ★ 推荐 |
| B. 实例化 | 11 中心 + 7 岗位各建一个 role code（18 个） | 直观 | role code 膨胀、权限矩阵 18 行、难维护 | 不取 |

**推荐 A 理由**：11 中心 + 7 岗位是「同类角色的不同数据范围」，参数化已在前端跑通（`scopedData` 按 centerId/expenseType 过滤），无需膨胀 role code。
