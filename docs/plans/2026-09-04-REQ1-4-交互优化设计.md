## 1. RK1 · 规则卡 ↔ 经济事项 两种可切换绑定（REQ-001）

**落点**：`website/views/rules.js` Tab3「适用经济事项」
**现状**：Tab3 = 上规则卡横向条（`.evt-cards`）+ 注释框（`.evt-comment`）+ 下经济事项平铺勾选列表（`.evt-list`，无树形），仅「选规则卡→勾选科目」单向。
**设计**：
- 顶部新增模式切换器 `.evt-mode-sel`（两种：① 规则卡→事项 ② 事项→规则卡），默认 ①。
- **模式①（左规则卡 + 右树形经济事项）**：左侧复用现有规则卡（`.evt-cards`，显示规则名/政策/弹性徽章）；右侧改为**树形经济事项**（新 `.evt-tree`，走 E1-E6 已建 4 级分类树 146/300，可展开折叠、勾选），选中规则卡时高亮其已映射事项（复用 `BM.RULE_EVENT_MAP` / `saveEventMap`）。
- **模式②（左树形经济事项 + 右规则卡）**：反转左右，选中经济事项节点→右侧高亮/勾选对应规则卡。
- **保存逻辑 `saveEventMap` / 加载 `/api/rule-versions/{id}/event-map` 不变**，仅 Tab3 内部结构 + 模式切换器；映射数据契约保持。
**影响**：仅 Tab3 内部；守住 `rules_event_map.e2e` 22/0。
**回归**：`rules_event_map.e2e`（22/0）、`grouping`、`create_next_rule`。

## 2. RK2 · 预算跟踪页「预算排行榜」（REQ-002）

**落点**：`website/views/kanban.js`（主；`track.js` 为可选扩展，本期不做）
**现状**：kanban 仅有组织/维度卡片（预算/执行/执行率/进度条/超支预警），无按超支幅度分档排序的排行榜；已天然带**组织树下钻 + 年/季/月三层时间**。
**设计**：
- 在现有组织/维度卡片**上方**新增独立区块「预算排行榜」（`.kb-rank`）。
- **柱状图**：每个超支科目/聚合项一根纵柱，高度=超支幅度（降序排列）；三档色：超 50% = 红（`danger`）、超 30% = 橙（`warn`）、超 10% = 黄（过渡），未超不进榜（或单列「可控」区）。
- **数据**：复用 `BM.kanbanAgg(items, period, dim)` 产出的 `devPct` / `rate` / `warn`，按超支幅度分档聚合；与卡片同源（`BM.loadKanbanData`）。
- **层级联动**：随 kanban 现有 `state`（组织下钻 `orgPath` + 时间 `period` 年/季/月）自动重算——即「组织层级 + 时间层级」双联动，无需另写筛选。
- 与现有卡片并存，不替换。
**影响**：仅 kanban.js 新增区块 + 相关 CSS（`.kb-rank` / 柱体类）；复用既有聚合与加载链路。
**回归**：kanban 相关 E2E、wb-home-diff、role-convergence。

## 3. RK3 · 编制页「编制理由」列（REQ-003）

**落点**：`website/views/compile.js` 经济事项视角 8 列填报表
**现状**：8 列（经济事项/会计科目/本年度预算值/上年预算/上年决算/偏差/AI 建议/月度拆分），无「编制理由」列；但数据层 `BM.compileSaveSubject`（:92）与 `BM.compileSaveDraft`（:435）的 subject item **已带 `reason: ""` 字段**，从未赋值/展示。
**设计**：
- 在 **AI 建议列之后、月度拆分之前** 新增「编制理由」列（`<th>编制理由</th>` + `<td>` 内可编辑输入，建议 `textarea` 单行或 `input`，行内变更即存）。
- **落库**：行内输入 → 存 `compileSaveDraft` 的 `items[cat].reason`（既有字段，无需改数据模型）；渲染时回填草稿 `draft.items[cat].reason`。
- **API 模式**：本期先离线草稿模式落地；理由后端持久化（`/api/events/{id}` 当前 PUT 仅传 `amount`）标为**后端扩展点**，拆解/联调时再补（不在本批阻塞）。
- 形成「AI 依据 ↔ 我的理由」对照（AI 建议列在左、编制理由在右）。
**影响**：仅 compile.js 加列 + 行内存读；零数据模型迁移。
**回归**：compile 视图 E2E、草稿恢复。

## 4. RK4 · 编制流程「规则自动分解」免手填（REQ-004）

**落点**：`website/views/compile.js` + `website/core/calc.js`（引擎已就绪）
**现状**：`renderFillTable` 对**每一行**都渲染手动滑块+数值输入（不分方法）；`compileByMethod`（calc.js:130/134）已支持 `perCapita`（人均标准=在编人数×人均，desc「如食堂/宿舍」）/ `volume`（业务量×单位成本）确定性计算，`note` 已含「人均标准：h 人 × pc」分解口径。
**拍板范围**：`perCapita` + `volume` 算「规则自动分解、免手填」。
**设计**：
- 按 `BM.CTRL_METHOD_ASSIGN[cat]` 的 method 区分两类：
  - **自动分解类**（`perCapita` / `volume`）：系统经 `compileByMethod` 算出的预算**自动填入**并落库；行内**禁用滑块/输入（锁定）**，显示「**自动分解**」badge + **分解口径**（如「人均 200 元 × 50 人 = 10,000」取自 `compileByMethod` 返回的 `note`）。用户无需、也不能手填。
  - **填报类**（其余 method：history/yoy/fixed/manual/manageStd/keyEvent 等）：保持现有手动滑块 + AI 建议入口不变。
- 与 RK3 同页共存：自动分解行的「编制理由」列仍可填（理由独立于金额来源）。
**影响**：仅 compile.js 行渲染分支（按 method 判定锁定/展示）+ 少量 CSS；计算内核 `compileByMethod` 不动。
**回归**：compile 视图 E2E、test_calc.js 的 `compileByMethod` 单测（已覆盖 perCapita/volume）。

## 5. 影响评估（pre-change-impact-analysis 摘要）

- **Q1 全树去重/复用**：RK3 的 `reason` 字段、RK4 的 `compileByMethod` 引擎**均已存在**，本批是「接上 UI/落库」，非重复实现 → 单一真源复用。
- **Q2 影响面**：
  - RK1 仅 `rules.js` Tab3 内部，映射契约不变；
  - RK2 仅 `kanban.js` 新增区块 + CSS；
  - RK3/RK4 仅 `compile.js` 行渲染 + 既有 `reason`/`compileByMethod` 复用；
  - 均不涉及 `server/` 数据模型迁移（RK3 API 持久化为标注扩展点，非本批阻塞）。
- **共享文件**：`index.html` / `harness.js` / smoke 测试加载清单**无需改动**（无新文件，仅改既有视图）。
- **风险**：RK1 重构 Tab3 结构需守住 `rules_event_map.e2e` 22/0；RK3/RK4 同在 compile.js 需避免行渲染分支冲突。
