## 一、需求与已拍板决策

### 1.1 四大需求
1. **登录后首页"核心功能"导航卡片与顶部菜单重复** → 删除首页卡片，顶部 `quicknav` 菜单作为唯一功能导航。
2. **新建消息推送模块**：按角色 / 数据范围只推送与该用户相关的预算业务消息（基层看不到组织架构、部门汇总、账户角色等无关消息）。
3. **Excel 客户真实主数据全量导入测试库**：经济事项 + 科目、组织部门、单位预算明细。
4. **预算规则独立成可版本化管理模块**：规则动态变化，按预算会议 / 收入方案 / 预算文件生成新规则或修改规则，形成新的预算版本。

### 1.2 已拍板决策
- **D1 数据导入 = 全量重建**：用 Excel 真实数据重建 `organization`（42 家公司 + 事业部 + 生产单元 + 职能中心 + 一级部门）和 `economic_event` / `unit_budget`（全量经济事项 + 科目编码 + 归口部门 + 2026 预算 + 12 月拆分），替换现有演示的 `HQ/4公司/12部门` 与 6 条种子。
- **D2 消息模块 = 骨架 + 种子**：建 `notification` 表 + 按角色/范围过滤 API + 前端铃铛红点 + 工作台按角色展示种子消息；业务动作动态生成后续接入。
- **D3 "管理中心" = 职能中心 / 预算归口部门**：指 Excel 的「预算归口部门」（IT、总办、人资、战略、财务等 59 个归口值），作为职能中心节点纳入组织树，对应现有 `centerOwner` 角色。
- **D4 预算规则模块 = 混合生成（2026-08-24 定稿）**：范围 = 控制基线逻辑（down5/canteen/dorm… 各经济事项下降比例与基线方法）+ 财务流程规则（planMode/trackMode/surplusAction/allowOverBudget）**一并纳入同一版本框架**；新版本生成 = **混合过程**：AI 仅做"读文件/纪要→抽取变更建议"（不碰库），确定性规则引擎按人确认的结果实际生成条目，人审核发布；两种入口并存（有文件/纪要走 AI 抽取辅助，无文件走确定性批量调整）；遵循项目铁律「LLM 经 prompt 抽取，规则仅作护栏校验」。

### 2.2 `organization` 表（全量重建，level 维度）
| level | 来源 | 父节点 | 规模 |
|---|---|---|---|
| group | 公司对照表「三安光电股份 1000」→ HQ | — | 1 |
| business | 事业部生产单元对照表「事业部组织编码/简称」 | HQ | ~9 |

| center | 预算归口部门去重（IT、总办、人资、战略、财务、采购、品管、基建、风控、证券、销售、技术中心…） | HQ | ~20 |

### 2.3 `economic_event` 表（经济事项主数据）
- `cat` = 预算科目名称（费控科目明细表去重，几百条）
- `acct_code` = 会计科目编码（如 6600010124）
- `center` = 归口部门（关联 organization 的 center 节点）
- `method` = 控制逻辑（由「预算逻辑」表匹配：下降5%→`down5`、据实→`actual`、匹配不到→`manual`）
- `amount` / `monthly` / `last_budget` / `last_year` = 来自数据收集表(2)按科目跨公司汇总 + 文件C 历史
- 偏差 = `last_year − last_budget`（查询计算，不落库，保持现状）

### 2.4 `unit_budget` 表（单位 × 事项明细）
- 来源：数据收集表(2) 3198 行 → `org_id`(公司) × `cat`(预算科目) × `amount`(2026) × `monthly`(12月) × `center`(归口部门)
- 量级：约 3000+ 行（SQLite 无压力）

## 三、消息推送模块设计

### 3.1 后端：新表 `notification`
| 字段 | 说明 |
|---|---|
| id | PK |
| user_id | 接收人（null = 按角色/范围广播） |
| role_scope | 可见角色（expense/staff/manager/finance/buHead/ceo/admin/all…）；排除逻辑见 3.3 |
| org_scope | 可选组织范围 |
| type | compile / execution / deviation / summary / org / account |
| title / body | 标题 / 正文 |
| view | 点击跳转视图（compile / kanban / org / accounts…） |
| ref_id | 关联业务 ID（可选） |
| priority | normal / danger |
| read | 0/1 |
| created_at | 时间 |

### 3.2 API
- `GET /api/notifications?unread=1` → 按当前用户角色 + org 过滤，返回列表 + 未读数
- `POST /api/notifications/:id/read` → 标记已读
- `POST /api/notifications/read-all` → 全部已读
- `POST /api/notifications`（admin） → 创建消息（种子 / 后续动态生成复用）

### 3.3 可见性约束（核心原则：只推相关）
- 基层角色（`expense` / `staff`）**不可见** `type ∈ {org, account, summary}` 的消息。
- `role_scope='all'` 的消息对全员可见（如编制通知）。
- `role_scope` 含当前用户任一角色 ⇒ 可见。
- `user_id = 当前用户` ⇒ 可见（个人定向消息）。

### 3.4 种子消息（演示各类）
| type | 内容示例 | 可见角色 | view |
|---|---|---|---|
| compile | 2026 年度预算编制通知 | 需编制角色（all） | compile |
| execution | XX 科目预算执行超标预警 | 相关角色 | kanban |
| deviation | N 项偏差预警待复核 | 相关角色 | kanban |
| summary | 部门预算汇总·编制完成 | 上级（finance/buHead/ceo…） | unitInbox |
| org | 组织架构更新 | admin / 上级 | org |
| account | 账户与角色变更 | admin | accounts |

### 3.5 前端
- 顶部导航（`app.js` / `index.html`）增加 **消息铃铛 🔔 + 未读红点 badge**；登录后拉取未读数。
- 点铃铛 → 下拉/弹窗列出按角色过滤后的相关消息，点击跳转 `view` 并标记已读。
- 工作台首页（`workbench.js`）：
  - **删除「核心功能」导航区块**（第 50–64 行）。
  - 「预算业务提醒」改为调用 `GET /api/notifications`（替换现有硬编码 `buildReminders`），只展示相关消息。

## 四、预算规则版本化管理模块（D4 定稿·混合生成）

### 4.1 目标
把当前散落在 `db.js` 硬编码函数（`applyRuleBase` / `compileBaseline` 的 down5/canteen/dorm/revenue/green/actual 比例）与 `rules.js` 前端 state 的财务流程规则（planMode 等），统一改为 **数据库可配置 + 版本化管理**。规则可按预算会议 / 收入方案 / 预算文件生成新版本，形成版本历史。

### 4.2 数据模型
**`budget_rule_version`（规则版本集）**
| 字段 | 说明 |
|---|---|
| id | PK |
| version | 版本号（如 `v2026.1`、`v2026.2`） |
| name | 版本名称 |
| source_type | 来源类型：meeting / income-plan / budget-file / manual |
| source_ref | 来源引用（会议 ID / 方案名 / 文件名） |
| effective_date | 生效日期 |
| status | draft / active / archived |
| created_at / created_by | 创建信息 |
| note | 版本说明（如"根据 8 月预算会议决议，整体下调 1%"） |

**`budget_rule_item`（版本下的规则条目，覆盖两套规则）**
| 字段 | 说明 |
|---|---|
| id | PK |
| version_id | 所属版本 |
| category | `baseline`（控制基线逻辑）/ `flow`（财务流程规则） |
| scope_type | `global` / `type`（费用类型 down5 等）/ `cat`（经济事项）/ `center`（职能中心） |
| scope_key | 作用域键（如 `down5` / `总办办公费` / `IT`） |
| method | 基线算法（manageStd/volume/qtyPrice/history/manual…） |
| factor | 参数（如下降比例 0.95） |
| base_logic | 文字逻辑（"较2025实际下降5%"） |
| raw | 原始逻辑文本（来自 Excel 预算逻辑） |

### 4.3 初始版本迁移（硬编码 → DB）
- 启动时若 `budget_rule_version` 为空，自动写入初始版本 `v2026.0`（active），其 items：
  - baseline 类：由 `applyRuleBase` 现有映射生成（`down5`→0.95、`canteen`→0.97、`dorm`→0.90、`revenue`→0.98、`green`→0.92、`actual`→1.0），`scope_type=type`。
  - baseline 类另补 per-cat 逻辑：由 Excel「预算逻辑」sheet 的"2026年预算逻辑"映射（如"较2025实际费用下降5%"→factor 0.95，`scope_type=cat`）。
  - flow 类：由现有 `BM.state.rules` 默认值生成（planMode=bottomup、trackMode=reimburse、surplusAction=reclaim、allowOverBudget=false），`scope_type=global`。
- `compileBaseline` / `aiSuggestion` / 编制基线计算改为 **读取 active 版本的 rule_item**（按 scope 匹配 type→cat→center→global 优先级），不再硬编码比例。

### 4.4 版本生成工作流（混合过程，D4 定稿）
两种入口，最终都过"人审核发布"，**AI 不直接入库**：

**入口 A（有文件/纪要 · AI 抽取辅助）**
1. 在「预算规则管理」页点「基于当前版本生成新版本」→ 系统克隆 active 为 `draft`。
2. 粘贴预算会议纪要 / 上传预算方案 / 预算文件 → 调用 LLM（已配 AWS Key）**抽取**出"建议变更清单"（如：总办办公费 下降5%→6%、食堂 据实、IT 统一降2%）。
3. 页面把清单列给用户**核对**（可逐项确认 / 微调 / 驳回）。
4. 用户确认后，**确定性规则引擎**按确认结果生成 draft 版本的 rule_item（factor/method/base_logic），AI 不碰库。

**入口 B（无文件 · 确定性批量）**
1. 同上克隆为 draft。
2. 用确定性公式批量调整（如"整体再降 1%"→ 所有 baseline 条目 factor×0.99；或按职能中心 / 类型逐项改）。
3. 财务流程规则（flow 类）也可在此调整。

**共同收尾**
3. 填写来源：`source_type`（会议/收入方案/预算文件/手动）+ `source_ref` + `note`（变更说明）。
4. 点「发布为新版本」→ 旧 active 置 `archived`，新版本置 `active`，立即生效（全系统 baseline / AI 建议 / 编制基线随之变化）。
5. 版本历史列表可查看任意版本、对比差异、回滚（将某 archived 版本重新发布为 active）。

### 4.5 API
- `GET /api/rule-versions` → 版本列表 + 当前 active
- `GET /api/rule-versions/:id` → 版本详情（含 items）
- `POST /api/rule-versions` → 克隆当前 active 为 draft（或手动新建）
- `PUT /api/rule-versions/:id/items` → 修改条目（批量/逐项）
- `POST /api/rule-versions/:id/publish` → 发布为新 active（旧版本 archived）
- （admin / finance）写权限控制
- `POST /api/rule-versions/:id/extract`（可选） → 接收纪要/文件文本，调用 LLM 抽取建议变更清单返回（不写库，仅供核对）

### 4.6 前端模块（`rules.js` 改造为「预算规则管理」）
- 当前生效版本展示：基线规则（按经济事项/类型/职能中心）+ 财务流程规则。
- 版本历史列表：版本号 / 来源 / 状态 / 生效时间，可查看、对比、回滚。
- 「生成新版本」工作流：克隆 →（粘贴纪要走 AI 抽取 / 或确定性批量）→ 人核对 → 标注来源 → 发布。

## 八、实现期决策（松哥可纠偏）
1. **组织层级映射**：采用「HQ → 事业部 → 生产单元」「HQ → 公司 → 一级部门」「HQ → 职能中心」三棵树并存于同一 `organization` 表（parent_id）。若你希望事业部下挂公司、或职能中心挂到公司，请指明。
2. **编制主表粒度**：`economic_event` 全量几百条后，编制表（compile）按经济事项列出（无公司维度，保持现状）。若需「公司 × 经济事项」二维编制，需另议。
3. **动态消息生成**：D2 仅做骨架 + 种子；编制提交 / 压降 / 汇总下发等业务动作触发真实通知，列为后续迭代（T2 预留 `POST /api/notifications` 接口）。
4. **预算规则 AI 抽取**：D4 入口 A 的 LLM 抽取遵循「LLM 经 prompt 抽取，规则仅作护栏校验」——AI 只产出建议清单供人核对，不直接写库；具体 LLM 接入方式（AWS 已配 Key）在实现 T6 时落地。
