## 1. 背景与诉求
1. **预算工作人员（用户）管理**：系统已有「账户与角色」页（admin 专用，建用户 / 绑组织 / 分配角色）。松哥要求把它定位为**预算工作人员管理**，放在**组织架构之后**，并强调**用户 ↔ 部门**的归属关系。
2. **管理中心 ↔ 部门归口关系**：现有会计科目 / 经济事项有「归口中心」字段（如职能中心、行政服务中心等散落值），需要把组织树里的**部门 / 单位**与 **11 个管理中心**之间的**归口 / 管理关系**建立起来并可维护。

## 2. 对齐结论（2026-08-24 拍板）
| 决策点 | 结论 |
|---|---|
| 预算工作人员页 | **复用**现有「账户与角色」页（`website/views/accounts.js` + `GET/POST/PUT /api/users`），改名「预算工作人员」，导航挪到**组织架构之后**；强调用户↔部门归属 |
| 11 管理中心来源 | 作为 `organization` 树里挂在 HQ 下的**新节点类** `type='center'`（现有 company/dept 统一为 `type='unit'`/`'dept'`），不新建独立字典表 |
| 归口关系模型 | 每个部门/单位**单向归属一个**管理中心（`managed_center_id` → 中心节点 id），**一对多**（1 中心管 N 部门），预留将来多归口扩展 |
| 用户↔部门 | `user.org_id` 已能挂组织节点，在「预算工作人员」页把「所属部门」做清楚、可编辑即可 |

## 3. 数据模型
### 3.1 organization 表扩展
- 现有列：`id, code(唯一), name, parent_id, level`。
- 新增列：
  - `type TEXT`：节点分类。取值 `group`(总部) / `unit`(二级单位, 原 level=company) / `dept`(三级部门, 原 level=dept) / **`center`(管理中心)**。
  - `managed_center_id INTEGER`：本节点归属的**管理中心 id**（仅 `unit`/`dept` 用；`center` 与 `group` 为 NULL）。
- 兼容性：`level` 列保留（深度语义），`type` 为新增业务分类；历史数据通过迁移脚本回填 `type`（company→unit, dept→dept, HQ→group）。
- 新增 11 个管理中心节点（挂在 HQ=id1 下，`type='center'`，`level` 取 group 下一级，由 `recomputeOrgLevels` 推导为 company 层深度——需注意：center 与 unit 同级深度，靠 `type` 区分，不靠 `level`）。

### 3.2 归口关系
- 不建独立中间表（一对多，`managed_center_id` 直接落在组织节点上即可）。
- 若将来要支持"一个部门归多个中心"，再升级为 `department_center(org_id, center_id)` 中间表；本期不做。

### 3.3 用户 ↔ 部门
- `user.org_id` 已存在，指向 `organization.id`（可指向 `unit` 或 `dept` 或 `center`）。
- 「预算工作人员」页编辑时，「所属部门」下拉从组织树扁平化得到，显示层级缩进。

## 4. 后端 API（`server/server.js` / `server/db.js`）
### 4.1 organization 扩展
- `db.js`：
  - `createOrg`：新增 `type`（默认 `unit`）、`managedCenterId` 参数；校验 `managed_center_id` 指向的节点 `type='center'`（否则报错）。
  - `updateOrg`：同步支持改 `type` 与 `managed_center_id`；改 `managed_center_id` 时做存在性+类型校验。
  - `deleteOrg`：守卫新增——若节点 `type='center'` 且有部门 `managed_center_id` 指向它（即 `SELECT COUNT(*) FROM organization WHERE managed_center_id=?`），拦截并提示"该管理中心下仍有 N 个部门，无法删除"。
  - 迁移：`ALTER TABLE organization ADD COLUMN type TEXT; ADD COLUMN managed_center_id INTEGER;`；回填 `type`；插入 11 个管理中心种子（code 如 `MC-01`…`MC-11`，name 待定）。
- 路由：`GET /api/orgs/tree` 返回节点带 `type` / `managedCenterId`；`PUT /api/orgs/:id` 接受并落库。

### 4.2 预算工作人员（沿用现有）
- `GET/POST/PUT /api/users` 已支持 `orgId` / `roleCodes`，无需大改；「预算工作人员」页即 `renderAccounts` 改名。

## 7. 风险与防护
1. **迁移安全**：`organization` 加列 + 回填 `type` + 插 11 管理中心，需在迁移脚本里幂等（先查后插），不破坏现有 116 unit / 16 dept。
2. **删除守卫扩展**：center 节点删除新增"仍有部门归口"拦截；unit/dept 删除沿用现有 children/unit_budget/users 三道守卫。
3. **环检测**：改 parent 时拒环（已上线）；center 不能作为自己的归口（建 `managed_center_id` 时类型校验 + 防自指）。
4. **预算影响**：归口关系仅改展示/聚合口径，不动 `unit_budget.org_id` 已有预算数据；如需按新管理中心聚合预算，另议（本期只建关系，不动预算计算）。
5. **编码红线**：写操作补回归测试（API 单测 + E2E）；真机验证删除拦截后再宣称完成。
