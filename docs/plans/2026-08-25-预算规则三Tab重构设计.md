## 一、背景与目标

现有「预算规则」页（`rules.js`）已具备：当前生效版本卡片、`budget_rule_version`/`budget_rule_item` 版本化（克隆/发布/回滚）、以及一张**写死在 `data.js` 的 `BM.RULE_EVENT_MAP` 静态对照表**（规则代号 → 适用经济事项）。

本次将页面重构为 **「预算规则」三 Tab**，并做两处实质升级：
1. 导航/文案由「预算规则」改名为「预算规则」（语义更贴"基线因子即对明年的预测"）。
2. 「适用经济事项」从静态映射升级为**可编辑、落库**的按规则卡定义。

> 注：仅重构 UI 与补充数据/接口，**复用现有 `budget_rule_version` 表与版本 API**，不另起数据体系。

## 二、页面结构（三 Tab）

入口：`#rules`（权限 `requireRuleEditor`：admin / finance；其余角色见只读空态）。

### Tab1 · 当前版本
- **上部：规则项卡片**。取 active 版本的 `category='baseline'` 因子项（down5 / canteen / dorm / revenue / green / actual / volume / qtyPrice / history / manual），每个卡片展示：`scopeKey` + 因子百分比 + 方法标签。
  - **单选交互**：点击某卡片 → 下方解释区显示该卡片的 `base_logic`（如"较 2025 实际下降 5%"）+ `policy` 表述。默认选中第一项。
- **下部子区块：财务流程规则**（flow 项，非卡片平铺）。以只读小列表展示 `planMode / trackMode / surplusAction / allowOverBudget` 当前取值（编制方式 / 执行追踪方式 / 期末余量处理 / 超预算处理）。
- **操作：「调整并发布新版本」按钮** → 复用现有"克隆当前 active 为草稿 → 调因子 / AI 抽取 → 发布"向导流程（逻辑不变，仅入口收拢到此处）。

### Tab2 · 历史版本
- **列表行**：版本号 / 名称 / 状态徽标（active / draft / archived）/ 来源 / 创建时间 / 生效日期 / 备注。
- **行内操作**：
  - **恢复为当前版本**：对目标版本调 `POST /api/rule-versions/:id/publish`（archive 当前 active、目标置 active）。目标已是 active 时按钮禁用。
  - **删除**：调 `DELETE /api/rule-versions/:id`（见第五节守卫）。draft / archived 可删；**active 禁止删**（保证系统始终有 1 个生效版本）。删除前确认弹窗。
  - draft 版本行额外提供「编辑因子 / 发布」入口（复用既有 PUT items + publish）。

### Tab3 · 适用经济事项
- 把现有静态 `BM.RULE_EVENT_MAP` 改为**按规则卡可编辑、存库**。
- 布局：左列 = 规则项卡片（同 Tab1 的 baseline scopeKey）；右侧 = 该卡片「适用经济事项」多选清单（数据源 = `account_subject` 主数据，60 条科目）。勾选即关联，取消即解除。
- 保存：调 `PUT /api/rule-versions/:id/event-map`（整版本映射覆盖写）。读取：`GET /api/rule-versions/:id/event-map`。
- 落库后，`BM.RULE_EVENT_MAP` 改为从后端映射表加载（不再前端推导）；编译/AI 建议后续可消费，本轮仅完成"定义 + 展示 + 持久化"。

## 三、数据模型改动（仅新增，不改现有表）

新增表（幂等建表，迁移脚本不破坏既有版本数据）：

```sql
CREATE TABLE IF NOT EXISTS rule_item_event (
  id         INTEGER PRIMARY KEY AUTOINCREMENT,
  version_id INTEGER NOT NULL,
  scope_key  TEXT    NOT NULL,   -- 对应 budget_rule_item.scope_key（down5 等）
  subject_id INTEGER NOT NULL,   -- 关联 account_subject.id
  created_at TEXT DEFAULT (datetime('now','localtime'))
);
CREATE UNIQUE INDEX IF NOT EXISTS uq_rule_event ON rule_item_event(version_id, scope_key, subject_id);
```

> **待定稿确认项 A（关联粒度）**：默认按 `account_subject`（科目主数据，已建 60 条）关联；备选按 `economic_event.cat`（经济事项分类名，与现有静态映射一致）。倾向科目主数据（更稳定、可编辑 UI 已有）。

## 四、API 改动

| 方法 | 路径 | 说明 | 权限 |
|---|---|---|---|
| DELETE | `/api/rule-versions/:id` | 删除版本；守卫见下 | requireRuleEditor |
| GET | `/api/rule-versions/:id/event-map` | 返回 `[{scopeKey, subjectIds:[...]}]` | 登录 |
| PUT | `/api/rule-versions/:id/event-map` | body `[{scopeKey, subjectIds:[...]}]`，覆盖写该版本映射 | requireRuleEditor |

**删除守卫（DELETE）**：
- 目标 `status='active'` → 拒绝（400，`"生效版本不可删除"`）。
- 其余（draft / archived）→ 删除版本行 + 其 `budget_rule_item` + `rule_item_event` 关联（事务 BEGIN/COMMIT，node:sqlite 无 `.transaction()`）。
- 当前 schema 版本不被业务数据 FK 引用，不做"被引用拦截"；如后续加引用再补。
