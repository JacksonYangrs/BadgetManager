## 0. 核心约束与建设目标

**纲领**（邬亮）：「我们希望做系统，其实就是为了让更多的人进来参与，减轻我们做预算人的压力。」——决定功能设计核心导向。

## 2. 业务规则明确

### 2.1 填报维度：按经济事项「小类」填报（P1 · 待议）

**结论**（邬亮）：预算系统需细化填报维度，**按经济事项小类填报**。

**系统影响**：
- 填报入口按「经济事项小类」粒度组织，而非平铺或粗粒度科目；
- 与 V2 §3.3.2 已确认的「~390 项经济事项 + 会计科目编码 + 二级/三级分类」需建立对应关系。

**现状与缺口**：
- ⚠️ **部分覆盖**：V2 已有「经济事项 → 会计科目」映射与「二级/三级分类」字段，但「按小类填报」的下钻结构未在 demo 填报页（`compile.js`）明确落地。
- ❓ **待确认**：邬亮所述「小类」与 V2 科目字典的「二级分类 / 三级分类」是否同一套口径，需在正式设计中拉齐（原「大类—小类—部门」三级表述已收敛为「按小类填报」）。

### 2.2 后勤类预算按人头标准自动分配

**结论**：部分后勤类预算可按人头标准自动分配，**无需部门手动填报**。

**系统影响**：
- 后勤类科目（食堂、宿舍、办公、水电等）由系统按「人数 × 人均标准」自动生成，基层不手动填；
- 人数、人均标准作为基础数据维护，编制时自动带出金额。

**现状与缺口**：
- ✅ **设计已覆盖**：`docs/product/预算编制分层规则方案.md` 规则 3 已定义「食堂预算 = 就餐人数 × 人均餐标 × 工作日」「办公费 = 人数 × 人均办公费」等公式；V2 §3.3.3 也有「人均标准」类规则（移动电话费 = 月人均 × 人数）。
- ⚠️ **落地待补**：demo 中「按人数核定」规则存在，但「自动分配、部门免填报」的完整闭环（人数来源、标准维护、自动带入并锁定）尚未串成一条完整链路。

### 2.3 滚动预算规则（P6 · 保留待议）

**结论**：邬亮提出公司采用**滚动预算**规则；**本轮关键决策未提及，保留为待确认项**。

**系统影响**（若采用）：
- 预算不再是「年初一次定全年」，而是按固定周期滚动更新（如按月/季度滚动，随实际执行滚动修订后续期间预算）；
- 数据模型需在「年 + 月度 1~12」基础上，支持滚动版本的生成、对比与留痕。

**现状与缺口**：
- ❌ **完全缺失**：全项目当前无「滚动预算」业务（现有数据模型为「年 + 月度」静态分解，无滚动更新机制）。
- ❓ **待确认（须先讨论对齐）**：滚动周期（月 / 季）、滚动窗口长度、滚动触发条件、与年度预算与费控导入的关系、滚动版本与年度批准版本的冲突规则——均未在本次反馈中明确，需单独对齐后再进入设计。

> ⚠️ 纪律提示：滚动预算属**新增业务规则**，按「讨论—设计—开发」门禁，须先与客户/松哥把上述 5 个待确认点闭环，才能进入设计文档与开发。

### 2.4 部署形态与权限：专网 + 最高权限移交（D3 / D4 · 已拍板）

**结论（已拍板）**：
1. 系统部署在**公司专网**上，与现有费控系统同部署，保障财务机密数据安全；
2. 交付后由**对方拥有最高权限**，**开发方无访问权限**。

**系统影响**：
- 部署目标从「公网 Demo（AWS EC2 `3.25.82.99:8300`）」转向「客户专网环境 + 费控同环境」；
- 权限设计须支持「交付后超级管理员 / 最高权限移交给客户，开发方账号移交后即锁定、无任何访问入口」。

**现状与缺口**：
- ⚠️ **部署形态变更**：当前线上为 AWS EC2 公网 Demo，专网属新交付形态要求，需在实施阶段单独规划。
- ⚠️ **权限移交待设计**：现有 `admin/ops/gm` 内建账号为 demo 用途，正式交付需提供「首次初始化 → 创建客户超级管理员 → 移交并锁定我方账号」的流程。

## 3. 功能优化建议

### 3.1 填报页备注说明栏（D5 · 已拍板）

**结论（已拍板）**：预算填报页面增加**备注说明栏**，支持填报人填写**调整理由**。

**系统影响**：
- 每个预算填报 / 调整项支持填写「备注 / 调整理由」；
- 备注须随预算项落库，供审核与追溯使用（衔接 V2 §5.2 协商闭环的「调整原因」留痕）。

**现状与缺口**：
- ❌ **数据层已有、UI 缺失**：`website/views/compile.js` 数据模型已有 `reason` 字段，但被硬编码为空串（第 105、449 行），填报界面**无备注输入框**。属"字段已预留、交互未实现"的小改动。

### 3.2 跟踪页排序 + AI 管控建议（P2 / P3 · 待议）

**结论**：预算跟踪页按**超标、执行率异常**等维度排序展示，**强化 AI 分析的管控建议输出**与风险提醒。

**系统影响**：
- 跟踪页（`track.js`）需支持按「超标金额 / 超标比例 / 执行率异常」等多维排序与筛选，把异常科目置顶；
- 在现有 AI 预警基础上，升级为「AI 管控建议 + 风险提醒」（不止"预警"，还给出"建议怎么办"）。

**现状与缺口**：
- ⚠️ **AI 预警已有、排序缺失**：`website/views/track.js` 已实现「AI 追踪预警摘要 + AI 偏差归因 + 偏差高亮」（对应 V2 目标二），但**无按超标 / 执行率排序逻辑**，也未输出「管控建议」话术。
- ❌ **「AI 管控建议」待补**：现有 AI 输出为"预警/归因"，需扩展为"建议动作"（如"建议冻结该科目追加""建议约谈责任单位"），属目标二/三的增量。

## 4. 功能确认与数据对接

### 4.1 预算明细表导出（P4 · 待议）

**结论**：预算完成后支持**明细表导出**（会上口头确认可实现）。

**系统影响**：预算编制 / 汇总完成后，可按需导出明细表（含组织、科目、金额、月度分解、备注等字段）。

**现状与缺口**：
- ❌ **口头承诺、代码未落地**：demo 编制页当前**无导出按钮**；现有导出仅见于费控导入模块的「模板下载 CSV」（`import-view.js`）与数据层 `export` 函数，编制明细导出需新增。

### 4.2 费控数据对接（D2 · 已拍板）

**结论（已拍板）**：**由对方协调确认费控系统是否可提供 API 接口**，用于预算跟踪数据自动同步。无 API 时手动定期导入；有 API 时自动同步。

**系统影响**：数据对接分两档——无 API 走人工 Excel 定期导入；具备 API 后升级为自动同步（实时/准实时）。

**现状与缺口**：
- ✅ **已覆盖（一期形态）**：`import-view.js` 已实现「费控 Excel 导入」入口（模板下载 + 字段映射 + 对账 + 重复检测），对应 V2 §3.4.6「一期人工 Excel、暂不接 API」。
- ⚠️ **「有 API 自动同步」待对方确认**：是否提供 API 接口由对方协调确认，当前未开发。确认结果直接影响目标二的自动化程度。

### 4.3 月度总结报告推送（P5 · 待议）

**结论**：系统支持**月度总结报告推送**功能（会上口头确认）。

**系统影响**：系统按月自动生成预算执行总结报告，并推送给相关责任人。

**现状与缺口**：
- ⚠️ **部分覆盖**：消息模块（M6）已具备通知与推送基础能力，但「月度总结报告自动生成 + 推送」尚未落地——需明确报告模板、生成周期、推送对象与渠道。
