# 代码健康度评估（D 线开发前基线）

> 版本：V1（2026-09-02）
> 性质：三方评审汇总存档，作为 **D 线开发前基线**
> 评估方：PM（逐文件实证）+ 前端开发（sanan-frontend-dev）+ 后端开发（sanan-backend-dev）
> 评估对象：`server/`（Express + SQLite 后端）与 `website/`（vanilla JS 前端，含 `mobile/`）

---

## 1. 评估目的与范围

- **目的**：在进入 D 线（基础数据替换、权限移交、专网部署、费控 API）开发前，对现有代码做一次全量健康度体检，产出可回溯的基线，供后续开发「带着既有债务的清醒认知」推进，也作为 D 线前后健康度对比的基准。
- **方法**：三方并行独立评审（PM 逐文件实证 + 前端 / 后端各读自己域代码），返回结构化评价，由 PM 汇总去重、按置信度与优先级排序。
- **范围边界**：只评「现有代码的工程健康度」，不评业务需求正确性（那是 Sponsor 与产品线的事）；只做评估，不做改动（本评估之后的 P0 三件加固另立任务执行）。

---

## 2. 总体结论（三方定性一致）

| 维度 | 结论 |
|---|---|
| **定性** | 「Demo 可用、工程化半途」 |
| **成熟度评分** | 后端 ≈ 6.5/10，前端 ≈ 6.5/10（三方独立打分趋同） |
| **一句话判断** | 产品演示能力已充分（多角色、多视图、AI Copilot、费控导入全链路可跑），但**工程化只走到一半**：数据权威、模块边界、迁移治理、前后端双轨这几件「地基」尚未收口，是 D 线开发最大的隐性风险 |

**核心风险（三方共识）**：业务状态**前后端双轨未打通**——前端 `localStorage`（`BM.state`）与后端 SQLite 各存一套，谁是权威未定。演示期无感，但 D 线一旦接真实数据、上真实权限、部署专网，双轨会成为返工与数据不一致的根源。

---

## 3. 健康度总览（后端 vs 前端）

| 维度 | 后端（`server/`） | 前端（`website/`） |
|---|---|---|
| 模块化 | ✅ 组合根 + 15 个模块文件（`modules/`），限界上下文清晰 | ❌ `window.BM` 全局命名空间，31 个视图文件无模块系统 |
| 确定性计算 | ✅ `pure-calc.js` / `pure-rule.js` 纯函数，可单测 | ⚠️ `engine.js` 硬编码预测/分析/建议 demo 文案 |
| 权限控制 | ✅ `middleware/auth.js` 集中式 + `resolveAllowedOrgIds` 后端 verifier | ⚠️ 前端权限闸门与后端并存，双轨未对齐 |
| 数据权威 | ⚠️ SQLite 是后端权威，但前端 localStorage 并存 | ❌ `state.js` 大量 mock 硬编码 + 「TODO 后端接入」未闭环 |
| 路由风格 | ⚠️ `server.js` 470 行内联路由 vs `buildXxxModule().attach()` 两种风格混用 | — |
| 迁移治理 | ❌ `try{ALTER TABLE}catch{}` 吞异常，无版本化 migration | — |
| 端口径契约 | ✅ `backend-consistency.test.js` 锁死前后端 `decomposeMonthly` 一致 | ✅ 同一套契约测试反向锁定前端 |

## 4. 共识问题清单（6 条 · 高置信）

> 三方独立评审中各自独立命中、去重后仍一致的问题，可信度最高，优先处置。

| # | 问题 | 证据 | 影响 | 优先级 |
|---|---|---|---|---|
| 1 | **双轨数据权威不清** | 前端 `localStorage`（`BM.state`）vs 后端 SQLite 各存一套 | D 线接真实数据/权限/专网时的最大返工源 | P1 |
| 2 | **前端 mock 硬编码 + TODO 未闭环** | `state.js` 内 `SUG001-003`、张伟/李静/张明远、厦门三安 2010、`requestPurchase` 硬编码 IT 12 万；`engine.js` 整段硬编码 demo 文案 | 演示数据与真实数据混淆，AI 结论不可信 | P1 |
| 3 | **server.js 内联路由 vs attach 风格不一致** | `server.js`（470 行）内联 events/subjects/orgs/users/copilot 路由；`expense-import`/`policy_rules` 走 `buildXxxModule().attach()` | 模块边界被内联 SQL 穿透（`db.prepare(...).get(org)`） | P2 |
| 4 | **迁移无版本化** | `db.js` 靠 `try{ALTER TABLE}catch{}` 吞异常做迁移 | 迁移不可回滚、不可审计，D1 换数据风险高 | P1 |
| 5 | **因子口径未完全收口** | `policy_rules.js` 为第三份因子实现 | 三份因子漂移，口径不一致 | P1 |
| 6 | **README 漂移** | `README` 仍写 `python3 -m http.server`，与实际 Express 现状脱节；`/api/roles` 鉴权标注与实际不符 | 误导上手与联调 | P1 |

## 6. 亮点（值得保留的工程实践）

- **后端组合根 + 限界上下文**：`db.js` 组合根注入，`modules/` 15 个模块文件职责清晰（organization / auth / subjects / events / budget-compile / budget-execution / rules / ai-* / notifications / expense-import）。
- **纯函数确定性计算**：`pure-calc.js` / `pure-rule.js` 无副作用、可单测，是「可审计、可追溯」哲学的正确落地。
- **跨端口径契约测试**：`backend-consistency.test.js` 锁死前后端 `decomposeMonthly` 一致，反向护栏防漂移。
- **安全细节到位（be-dev 补充）**：`copilot-retrieval.js` 白名单 + 全参数化 + 姓名脱敏；`ai-gateway.js` AES-256-GCM 密钥加密 + `maskSecret` + `redactSecrets`；`organization.js` 环检测 + 四道删除守卫。
