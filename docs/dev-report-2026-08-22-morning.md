## 二、回应松哥三点指示

### ① 视角索引：经济事项视角以「经济事项」为索引；财务视角以「会计科目」为首要
**PM 理解**：两个派生视角不只是"换套标签"，而是**首要索引轴不同**——同一份数据，两个受众各看各的主轴。

- **经济事项视角（编制 / 填报工作视角）**：行索引 = **经济事项（最细事实源）**。保留 2025 实际 / 编制方法 / 基线 / 申报额 / 月度分解 / 偏离原因。这是"填"与"逐项审"的视角，面向基层填报人与中心负责人。
- **财务视角（汇总 / 核对视角）**：首要轴 = **会计科目（`accountCode` 会计编码）**。按科目聚合经济事项金额 → 呈现「科目 → 金额 → 占比 → 与基线差 → 与执行对比」。这是"看 / 核对 / 上报"的视角，面向财务与集团。
- （可选第三视角）**管理指标视角**：首要轴 = **职能中心（11 中心）**，按中心聚合，承接管理线下达的指标 / 压降。

**落地建议**：`compile.js` 当前 `dualModes`（fin/mgt/both）应重构为**按首要索引切换**——`event`（经济事项视角）、`account`（财务视角）、`center`（管理指标视角）；`both` = 并排比对（同数据双索引对照，便于对账）。这与"单数据源双派生视角"完全自洽：切换的是主轴，不是数据。

### ② 主工作台重构：编制是年度短窗口，日常是报销监控 / 跟踪
**松哥点破的关键**：编制每年只集中做 ≤1 个月（常约 1 周），**不是日常主轴**；日常打开系统做的是报销在途监控、预算执行跟踪、异常预警、待我审批。因此主工作台不能堆满"编制待办"。

**PM 提议的新工作台结构**：

- **主工作台（每日默认首屏）= 运营监控中枢**
  1. 待我审批（全年持续有动作）
  2. 报销在途 / 监控（日报销流，跟踪状态、超时）
  3. 预算执行进度（按科目 / 中心实时执行率 + 超标预警）
  4. 异常 / 风险预警（来自 M7 风险筛查）
  5. 编制季入口（仅编制窗口期高亮；平时显示"下一周期倒计时 / 只读"）
- **编制工作台（compile）= 独立模块**：平时低调，编制期成为主入口之一；待办只显示"本周期可动作项"，不堆全量清单。
- **待办项大幅瘦身**：日常只显示"今天可动作"的（待审 / 在途报销 / 超标），不再把 100+ 编制项当日常待办。

**影响范围**：映射文档 §4.1 工作台设计、`BM.roleViews` / `BM.defaultView`（角色默认首屏）、`wb-home` 设计、`compile.js` 入口权重。

### ③ 命名 + 归属澄清（松哥 23:28 已定）：叫「预算控制的方法」，且由上面定义
- **命名纠正**：不叫"编制方法"。应称 **「预算控制的方法」**（budget control method）。
- **归属纠正**：方法**由上面（管理层/集团/中心负责人）统一定义**，不是每个人照着方法来编制。即：方法 = 挂在事项上的**自上而下控制手段**，用于约束/核对基层申报，而非基层自选的"编制套路"。
- **对当前设计的冲击（已核实）**：`compile.js` 第 180–188 行现让填报人在每行「编制方法下拉」(`<select class="cmp-method">`) **自选方法**、再"按法计算"生成基线 —— 正是被否定的"每个人照着方法来编制"模型，须改为：方法由上级预挂（**只读**），基层只报「申报额」，系统按该上级定义的预算控制方法生成「控制基线」并比对偏离。
- **数量（9 vs 6）**：松哥此轮未再提数量；但既属"上面定义"，则 9 法是否采用、含哪些，须以管理层/客户实际定义为据，仍属**待上面定义确认**（非我们替基层定）。演示继续标注"待上面定义确认"。
