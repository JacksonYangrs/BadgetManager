# 模块设计文档：expense-import（费控导入 · 对账）

## 一句话定位
把企业费控系统 / Excel 里的真实花费数据「接进来」，先做对账校验，再决定怎么落库。

## 业务说明
预算要和实际对比，但真实报销/采购数据在企业的费控系统里。这个模块就是「数据搬运 + 校验」的接口：

- 对账（reconcile）：拿到一行行原始数据（公司、部门、费用类别、金额、日期…），拿组织字典和科目字典去对——部门认不认得、科目认不认得、金额合不合法。
- 导入（commit）：校验全过时，才放行；真实写库口径待「数据对齐」确认，目前只返回校验结论，不落库。
- 谁会用到：财务/归口责任人批量导入；前端「费控导入」页二次确认。
- 为什么存在：手工一条条录太慢，批量导入 + 自动对账才能把真实数据喂进执行跟踪。

## 业务流程（业务视角）
1. 对账：每行导入数据映射到「部门ID / 科目ID」，统计匹配数与错误数、合计金额。
2. 校验接口：返回对账结果，前端二次确认。
3. 导入接口：只有 0 错误才放行，当前仅返回校验结论（真实写入待数据对齐）。

## 技术对口（速查）
- 文件：`server/modules/expense-import.js`
- 依赖：`middleware/auth`（auth + requireBaseDataEditor）
- 只读 `dbm.listSubjects` / `dbm.listOrgs` 做字典校验
- 关键能力：`buildImportModule(dbm).attach(app, db)` → `reconcile` / `/api/import/reconcile` / `/api/import/commit`

## 依赖与解耦
- 依赖入：`middleware/auth`。
- 依赖出：被 `server.js` 挂载路由。
- 共享资源：经 dbm 只读 subjects / organization 字典。
- 目标耦合度：松。解耦措施：与 server.js 解耦，独立挂载；前端一期仍走本地 mock，后续可改调本模块。

## 关键决策规则
- 导入落库口径待确认：① 用 code 还是 name 映射；② 年度额按月均摊还是按导入月份；③ 与企业费控字段对齐。当前不写库，避免口径错误污染数据。
