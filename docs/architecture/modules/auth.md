# 模块设计文档：auth（账户 · 角色 · 权限）

## 一句话定位
管「谁能登录、能看哪些页面、能干什么操作」——系统的身份与权限中枢。

## 业务说明
预算系统有十几种角色（集团 CEO、总经办、财务、事业部负责人、部门经理、基层费用岗、员工……），每个人能看到什么菜单、能改什么数据都不一样。这个模块就是这套「身份 + 权限」的落地：

- 账户与口令：登录、登出、会话（24 小时有效）。
- 角色字典：每个角色对应一套「可见菜单（views）」和「数据范围（scope：集团 / 本公司 / 归口 / 本人）」。比如基层员工只能看自己发起的采购，财务能看全局。
- 种子用户：内置一批演示账号（admin / 张明远 / 徐静 …），方便直接登录试用。
- 谁会用到：所有人登录即用；管理员在「账户管理」里增删改用户、分配角色。

## 业务流程（业务视角）
1. 登录：输入账号密码 → 校验 → 发一个会话令牌（token）。
2. 每次请求：带着 token → 系统认出你是谁、你有哪些角色。
3. 访问页面/接口：系统按角色白名单放行或拒绝（比如「预算工作人员」页只给 admin/财务/总经办等）。
4. 管理员：可新建/停用用户、改归属组织、改角色。

## 技术对口（速查）
- 文件：`server/modules/auth.js`
- 数据库表：`role`（角色字典）、`user`、`user_role`（用户-角色关联）、`session`（登录会话）、`notification`（消息，与此模块同建）
- 关键能力：`loginUser`、`getUserByToken`、`createUser`、`updateUser`、`listUsers`、`listRoles`、`userToDto`

## 依赖与解耦
- 依赖入：`organization.js`、`notifications.js`（初始化时顺便种消息）。
- 依赖出：被 `server.js`、各业务模块、前端账户页调用。
- 共享资源：session / user / role 表（与 middleware-auth 共用 token 机制）。
- 目标耦合度：中（扇出 2）。解耦措施：具体「接口权限」已抽到 `middleware/auth.js`，本模块只管身份与数据。

## 关键决策规则
- 菜单可见（views）与接口权限（requireXxx）是两个维度：views 管「看得到什么」，requireXxx 管「能调什么」。
- 数据范围（scope）决定「能看哪些组织的数据」，与菜单白名单配合形成完整权限模型。
