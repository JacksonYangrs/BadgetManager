# 模块设计文档：rules（预算规则 · 版本管理）

## 一句话定位
把「怎么算预算基准、怎么压降」沉淀成可版本化、可审计的规则，是「规则只作护栏」的承载层。

## 业务说明
预算不是随便编的，要有依据：比如「差旅费按营收比例」、「食堂按人数×标准」。这个模块就是这些「算法规则」的管理台：

- 规则版本：规则可以改，但改之前先clone成草稿，确认无误再发布，发布才生效——避免线上突然变算法。
- 因子：每类事项对应一套因子（如管理标准、按量、按人头），决定基准额怎么算。
- 事项映射：哪类费用用哪套因子。
- 谁会用到：财务/总经办配置规则；编制时自动套用；AI 建议也读这里的因子。
- 为什么存在：让编制有「统一的、可追溯的口径」，而不是每个人拍脑袋。

## 业务流程（业务视角）
1. 版本管理：生成新版本号 → 克隆草稿 → 调整因子 → 发布（切换生效）。
2. 因子读取：取当前生效版本；若没有，回退到内置默认口径（保证确定性）。
3. 事项映射：维护「事项 → 因子」对应关系。

## 技术对口（速查）
- 文件：`server/modules/rules.js`
- 数据库表：`budget_rule_version`、`budget_rule_item`、`rule_item_event`；共享 `policy_document`
- 关键能力：`getRuleFactors`、`compileBaseline`、`listRuleVersions`、`cloneRuleVersion`、`publishRuleVersion`、`updateRuleItems`、`getEventMap`

## 依赖与解耦
- 依赖入：`pure-  rule`（因子计算口径）。
- 依赖出：被 `events.js`（基准额）、`ai-budget-decision.js`（因子）调用。
- 共享资源：规则三表 + policy_document。
- 目标耦合度：中（扇出 1）。解耦措施：因子核心在 pure-rule，rules 只做持久化与版本治理。

## 关键决策规则
- 规则变更必须走「草稿 → 发布」，发布才生效，避免线上突变。
- `getRuleFactors` 永远有确定性回退，AI 未接入时也不破坏编制口径。
