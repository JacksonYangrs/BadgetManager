## 2. 角色责任边界

### 2.1 前端开发（兼 UI 设计）：交付主责

项目采用「**前端负交付主责**」机制：

- 前端负责把《产品设计稿 V1》与《软件设计架构分析 V1》转化为可交互、可演示、零控制台错误的界面。
- 若交付物在**界面还原度、交互逻辑、移动端适配、数据可视化、角色工作台差异化**上出现缺陷，无论根因在前端还是后端，前端均为第一责任人，负责牵头定位并推动修复。
- 后端与测试配合前端完成接口联调、数据修正与验证；PM 负责判定责任归属并组织返工。
- 该机制不豁免后端与测试的责任，但明确**交付体验的第一把尺在前端**。
- **页面设计汇报义务（Sponsor 要求）**：每个模块的页面设计完成后，须向 Sponsor 报告设计结果，由 Sponsor 审阅；前端实现约束（框架/页面复用、设计风格升级、新增页面补充、冲突调参即时反馈界面）以《产品设计稿 V1》§3.0 为准。

### 2.2 后端开发：数据与规则主责

- 负责数据模型、版本控制、计算规则、费控导入、AI 抽取结果的结构化存储。
- 对「金额正确性、版本一致性、接口契约稳定性、审计证据完整性」负主责。
- 任何金额/汇总/约束计算错误，由后端牵头修复并补回归测试。

### 2.3 测试：质量门禁主责

- 任何代码改动必须配套回归测试；外部服务功能必须真机验证后才可宣称完成。
- 对「零控制台错误、关键路径端到端通过、缺陷可复现」负主责。
- 有权因为 blocker 缺陷拒绝交付进入下一阶段。

### 2.4 PM：流程与协调主责

- 负责把 Sponsor 的意图拆成可执行任务，分派给前端/后端/测试。
- 负责维持「对齐 → 设计 → 开发」三段分离门禁；未过设计拍板，不得进入开发。
- 负责整理会议结论、待拍板清单、版本说明与交付物归档。
- **映射维护（Sponsor 2026-09-02 确立）**：维护《需求-产品功能-模块对应关系》文件；每日汇报「产品功能与代码映射关系」+「需求-产品功能-模块对应关系」两份文件的变化（见 §2.9）。
- **纪律监督（Sponsor 2026-09-02 确立）**：监督团队遵守 §2.6 / §2.7 / §3.5 等强制流程；一旦发现纪律违规，PM 须**第一时间向 Sponsor 汇报**（见 §3.6）。
- 不替 Sponsor 做业务拍板；遇到未覆盖点退回 Sponsor 确认或补设计文档。

### 2.4 PM 自主处置授权（Sponsor 明确授权边界）

Sponsor 明确授权：PM 在以下情形可**直接分派工作给其他 agent，无需逐次请示**：

- **设计缺陷**：设计文档内部的逻辑矛盾、遗漏、不可实现点，由 PM 组织修订或退回设计角色补正。
- **代码缺陷 / Bug**：实现过程中发现的缺陷、报错、回归失败、控制台异常，由 PM 直接分派给前端/后端/测试修复并跟踪闭环。
- **排障与返工**：缺陷定位、责任判定、修复验证，由 PM 牵头推进，不阻塞等待 Sponsor。

PM **仅在以下两类情况必须找 Sponsor**：

1. **需求理解有偏差或不清楚**：对需求范围、业务规则、客户口径把握不准，或新信息显示原理解可能偏差。
2. **重大事情**：范围或架构方向变更、对外承诺、验收结论、影响交付成本或周期的决策等（具体以 Sponsor 判定为准）。

其余事项 PM 自行决策并知会 Sponsor 即可。

### 2.5 Sponsor：方向与拍板主责

- 对需求范围、关键业务规则、待确认问题、架构决策（D1–D5 等）做最终拍板。
- 负责提供客户侧真实材料与反馈。
- 对交付物做最终验收；验收不过可要求返工或调整方向。

### 2.6 开发工程师强制流程（Sponsor 2026-09-02 确立 · 最高纪律）

> 任何一个代码开发任务，开发工程师（前端 / 后端）**必须**按以下顺序执行，缺一不可。

1. **影响评估（动手前，先于写任何代码）**：评估本次改动对其他模块的影响，回答两问——① 要改的这点逻辑，别的代码里是否已经做过（全树去重，复用单一真源，禁止重复实现）；② 改这处会影响哪些功能 / 视图 / 接口。
   - 依据：用户级 skill `pre-change-impact-analysis`（松哥 2026-08-27 拍板）。
2. **文件位置决策**：基于影响评估，决定——在哪个既有文件上编写，还是**需要新建一个模块文件**。若新建模块，须先写模块规格文件（`MODULE_SPEC.md` 或 `.workbuddy/module-specs/<module>.md`：职责单一 / 是否独立 / 依赖入出 / 共享资源 / 解耦措施），确认清楚后才动一行业务代码。
   - 依据：用户级 skill `module-structure-discipline`。
3. **开发 + 自测**：完成开发后，先自行验证（语法检查、单元 / 回归、关键路径冒烟）。
4. **报告**：向 PM 报告**代码位置**（改了哪些文件、哪些函数 / 端点）与自测结果，并**更新《产品功能与代码映射关系》文件**（本次任务对应的功能点 ↔ 代码映射，见 §2.9）。
5. **PM 评审**：PM 评审代码与「需求 + 设计文档」的一致性；不一致退回返工或补设计。
6. **移交测试**：PM 评审通过后，安排测试工程师测试。

### 2.7 测试工程师强制流程（Sponsor 2026-09-02 确立）

> 测试工程师对每个测试任务，按以下顺序执行，禁止"边测边补"。

1. **写测试用例**：测试前先写用例（覆盖正常路径 + 边界 + 异常）。
2. **写测试方案**：明确测试范围、环境、数据、步骤、通过标准。
3. **执行测试**：按方案执行并记录结果；关键路径须端到端 + 真机验证；发现 blocker 有权拒绝交付（质量否决权）。

### 2.8 Sponsor 决策/仲裁边界 vs PM 自主边界（Sponsor 2026-09-02 确立 · 永久规则）

> 一句话边界：**冲突 / 取舍 / 新增 / 对外 / 违规 → 找 Sponsor；执行 / 排期 / 修 bug / 既定程序 → PM 自主。**

Sponsor 明确：非冲突类的常规开发事务（含已拍板的既定下一步，如「先 A 后 B」的后续步骤）由 PM **直接执行、事后汇报，不再逐次请示**。Sponsor 只做**决策 + 仲裁**；任务先后顺序不找 Sponsor（PM 更清楚执行依赖）。

**必须找 Sponsor（拍板 / 仲裁）——6 类：**

| # | 情形 | 触发信号 |
|---|---|---|
| 1 | **需求冲突** | 两个需求打架、只能二选一，或某需求撞上既定约束（安全保密 / 减负导向） |
| 2 | **设计取舍** | 非平凡决策：技术选型、架构/模块边界、接口/数据模型、部署/迁移/风控/性能——PM 枚举 ≥2 方案 + 权衡 + 推荐，Sponsor 拍板 |
| 3 | **新增需求 / 需求理解偏差** | 不是修 bug，是「要做新东西」，或 PM 拿不准需求本意 |
| 4 | **范围扩张** | 超出已定稿设计文档 / 已拍板决策的内容 |
| 5 | **对外 / 不可逆动作** | 发布给项目方、对外消息/邮件、生产部署、资金、权限移交、删数据 |
| 6 | **纪律违规上报** | 出现违规，PM 第一时间如实上报（见 §3.6，奖惩 Sponsor 定） |

**PM 自主（不找 Sponsor）——非冲突类：**

- 任务排期 / 先后顺序（PM 比 Sponsor 更清楚执行依赖）；
- 常规 bug 修复 + 事后报告（见 §2.4）；
- 已定稿设计文档内的开发、自测、回归、git 提交、版本号 +1（见 §2.6 / §3.5）；
- 测试用例 / 方案 / e2e 执行（见 §2.7）；
- 影响分析、模块规格等纪律性前置动作（见 §2.6 步骤 1–2）。

### 2.9 产品功能-代码 / 需求-功能-模块 双映射维护（Sponsor 2026-09-02 确立）

> 一句话：**开发每完成一任务 → 更新《产品功能与代码映射关系》；PM 维护《需求-产品功能-模块对应关系》；两者每日变化都要汇报。**

| 文件 | 维护者 | 更新时机 | 映射内容 |
|---|---|---|---|
| `产品功能与代码映射关系.md`（项目根目录） | 开发工程师 | 每完成一个任务后 | 产品功能点 → 实现它的代码（文件 / 模块 / 函数 / API 端点） |
| `需求-产品功能-模块对应关系.md`（项目根目录） | PM | 需求 / 功能 / 模块变化时 | 需求 → 产品功能 → 模块的三级追踪 |

**维护要求**：

- **开发工程师**：每次完成任务，在报告代码位置的同时，把「本次实现/改动的功能点 ↔ 代码文件」写入《产品功能与代码映射关系》，不得遗漏、不得滞后（并入 §2.6 步骤 4）。
- **PM**：维护《需求-产品功能-模块对应关系》，把需求调研稿 / 产品设计稿中的需求点，向下映射到产品功能、再映射到模块；需求或功能变化时同步更新。
- **每日汇报**：PM 每日汇报时，报告两份文件的变化（新增 / 修改 / 删除的映射条目），见 §3.3。

## 3. 协作流程

### 3.1 标准任务流

```text
Sponsor 提出需求 / 拍板 → PM 拆解任务 → 设计（如需）→ 分派给前端/后端/测试
   ↑                                                                  ↓
   └←←←←←←←←←←← 最终验收 ←←←←←←←←←← QA 验收通过 ← 开发完成 ←←←←┘
```

### 3.2 阶段协作规则

| 阶段 | 主要角色 | 关键动作 | 门禁 |
|---|---|---|---|
| **对齐** | Sponsor + PM | 双向确认需求、风险、约束；PM 复述，Sponsor 确认 | 关键问题闭合后才能进入设计 |
| **设计** | PM + 前后端 + Sponsor | 出/审设计文档、架构决策对比、待拍板清单 | Sponsor 拍板后设计定稿 |
| **开发** | 开发工程师 + PM | 按设计文档实现；**须先走 §2.6 强制流程**（影响评估→文件决策→自测→报告代码位置→PM 评审一致性）；前端牵头交付体验，后端牵头数据规则 | 未过设计定稿不得开发 |
| **测试** | 测试工程师 + 开发工程师 | **须先走 §2.7 强制流程**（写用例→写方案→执行）；补回归测试、端到端验收、控制台检查、真机验证 | blocker 不通过则退回开发 |
| **交付** | PM + Sponsor | 演示、确认、归档、写工作记忆 | Sponsor 验收签字 |

### 3.3 每日 / 每轮同步规则

- **任务启动前**：PM 在对话中列出任务清单（编号、内容、预估、状态、优先级），请 Sponsor 引导排序。
- **开发中**：设计缺陷 / 代码缺陷由 PM 按 §2.4 自主分派修复并跟踪闭环；仅当需求理解偏差或范围蔓延时升级给 Sponsor。
- **完成后**：由执行角色自测，QA 复验，PM 审阅，Sponsor 验收。
- **每日映射汇报（Sponsor 2026-09-02 确立）**：PM 每日汇报时，报告《产品功能与代码映射关系》与《需求-产品功能-模块对应关系》两份文件的变化（见 §2.9）。

### 3.4 争议与升级

- **缺陷修复（不属升级事项）**：设计缺陷、代码 Bug、回归失败、控制台异常，按 §2.4 由 PM 自主分派修复并闭环；仅在修复过程揭示需求偏差时才升级 Sponsor。
- **技术实现争议**（如框架、接口、算法）：前后端先协商；协商不成由 PM 组织方案对比，报 Sponsor 拍板。
- **需求范围争议**：PM 不擅自扩展；回 Sponsor 确认，必要时补设计文档。
- **质量争议**：QA 拥有质量否决权；PM 组织三方（前后端/QA/Sponsor）判定 blocker 是否成立。
- **交付延期**：PM 提前向 Sponsor 预警，调整阶段优先级或范围。

### 3.5 Git 提交纪律（Sponsor 2026-09-02 确立）

- **提交频率**：每 2 小时 **或** 每完成一个模块（以先到者为准），进行一次 git commit，禁止长时间不提交导致改动堆积。
- **提交规范**：commit 语义清晰（改了什么）；版本号每次改动最小位 +1，本地与 AWS 一致，打 tag 后 push origin/main。
- **适用范围**：所有开发工程师，含 bug 修复、功能开发、文档更新。

### 3.6 纪律违规汇报机制（Sponsor 2026-09-02 确立）

> 一句话纪律：**出现项目纪律违规，PM 第一时间向 Sponsor 汇报；如实上报有奖励（由 Sponsor 判定发放）。**

- **违规判定范围（7 条，Sponsor 2026-09-02 拍板定稿）**：① 未走 §2.6 影响评估直接写码；② 新建模块未先写模块规格文件；③ 未按 §3.5 及时 git 提交导致改动堆积；④ 测试未先写用例 / 方案就执行（违反 §2.7）；⑤ 未过设计拍板擅自进入开发（违反三段门禁）；⑥ 需求理解偏差 / 新增需求未报 Sponsor 擅自扩范围；⑦ 未做回归测试 / 真机验证就宣称完成。
- **PM 义务**：发现违规**第一时间（当场、不拖延）**向 Sponsor 汇报，不隐瞒、不淡化、不自行消化了事。
- **汇报形式（双轨并行，Sponsor 2026-09-02 拍板）**：① **当场对话文字汇报**（发现即报，最即时）；② **落文件留痕**（记入 `TASK_BOARD.md` 与当日工作日志 `.workbuddy/memory/YYYY-MM-DD.md`，可追溯）。
- **汇报内容**：谁违规、违反哪一条、具体事实、影响范围、PM 已采取的处置或建议。
- **奖励**：PM 如实、及时上报违规，由 Sponsor 判定给予奖励；瞒报、迟报不适用奖励。

## 4. RACI 矩阵（一期关键活动）

| 活动 | Sponsor | PM | 前端 | 后端 | 测试 |

## 5. 交付物与质量标准

### 5.1 前端交付标准

- UI 与设计稿偏差不得影响业务语义（颜色/字号/间距在 5% 以内）。
- 角色工作台差异化：总经理、部门经理、员工、财务经理的入口、权限、默认视图必须区分。
- 移动端与桌面端核心流程均可完成，移动端优先保证查看与审批。
- 浏览器控制台无 error / 无未处理异常。
- 关键操作（提交、压降、协商、导入）有 loading、成功/失败反馈、回滚提示。

### 5.2 后端交付标准

- 所有金额计算有单元测试覆盖；边界场景（跨月、跨法人、跨科目、版本回滚）必须测试。
- 费控导入必须保留原始文件、解析日志、错误行号与修正轨迹。
- AI 抽取结果必须保存原始文本、解析置信度、人工确认状态；禁止 AI 直接写正式约束。
- 审计日志覆盖：谁、何时、改什么、由什么触发。

### 5.3 测试交付标准

- 每轮改动至少一条回归测试锁定关键行为。
- 端到端覆盖：登录 → 工作台 → 编制/导入/压降/协商/审批 → 导出/留痕。
- 控制台错误检查必须使用真实 Chrome（Playwright），不接受简化测试页。
- 外部服务（如有）必须真机验证；未验证不得报告完成。

## 6. 专家调用方式

三个交付角色已固化为 WorkBuddy 专家包，存放于 `~/.workbuddy/plugins/marketplaces/my-experts/plugins/`：

| 专家包 | 类型 | 主要能力 |
|---|---|---|
| `sanan-frontend-dev` | Agent | 前端/UI：Tailwind、vanilla JS、BM 命名空间、角色工作台、数据可视化、移动端 |
| `sanan-backend-dev` | Agent | 后端：FastAPI/SQLite、ER 建模、确定性计算、规则引擎、费控导入、审计 |
| `sanan-qa-tester` | Agent | 测试：Playwright、pytest、回归测试、零控制台错误、端到端验收 |

PM（本会话）负责根据当前任务调度对应专家，并传递：

- 必须遵循的设计文档路径。
- 本 TEAM.md 的责任边界。
- 当前任务的具体输入、输出标准与验收条件。
